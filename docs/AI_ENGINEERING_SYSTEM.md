# VoxFlame AI Engineering System

> 更新日期：2026-03-08
>
> 本文档基于 OpenAI 文章《Harness Engineering》（https://openai.com/zh-Hans-CN/index/harness-engineering/）对项目协作方式做的落地重构。

## 1. 为什么要重构

过去的 AI 编程指导主要依赖 `AGENTS.md`、`CLAUDE.md`、`.github/copilot-instructions.md` 这类入口文件承载大量信息。这个做法有三个问题：

1. 入口文件过长，混入了项目状态、历史结论、工具偏好和架构事实，阅读成本高，且极易过期。
2. 多个入口文件内容重复但不同步，导致不同智能体看到的规则不一致。
3. 任务计划、验证门禁和文档维护没有形成稳定的仓库内“工作环境”，仍然依赖临时提示词和人为记忆。

`Harness Engineering` 的核心启发不是“把 prompt 写得更长”，而是“把仓库本身改造成智能体可工作的环境”。

## 2. 从文章提炼出的核心原则

### 2.1 环境优于提示词

把稳定知识放进仓库文件、脚本、模板和测试，而不是塞进一段越来越长的系统提示。

VoxFlame 落地：

- 入口文件只保留短规则和文档地图。
- 深层规范进入 `docs/`。
- 机械检查进入 `scripts/` 和 CI。

### 2.2 短入口，深文档

文章强调入口提示应更像目录，而不是百科全书。入口负责把模型引导到正确位置，详细规则由仓库文档承载。

VoxFlame 落地：

- `AGENTS.md`、`CLAUDE.md`、`.github/copilot-instructions.md` 统一为短地图。
- 架构、流程、模板、状态分别落到专用文件。

### 2.3 计划是第一等工件

复杂任务不能只靠对话往前推。计划、假设、风险、验收标准需要显式存在。

VoxFlame 落地：

- 为复杂任务提供统一模板：`docs/AI_EXECUTION_PLAN_TEMPLATE.md`。
- 非 trivial 任务必须明确目标、影响面、验证和回退。

### 2.4 自主性必须绑定门禁

智能体应该尽量自主，但前提是有清晰的产品约束、代码约束和停止条件。

VoxFlame 落地：

- 明确产品优先级：可理解性 > 低延迟 > 可打断 > UI 精修。
- 明确工程门禁：强类型、服务分层、会话隔离、验证必做。

### 2.5 好的默认路径必须机械化

如果“正确做法”只能靠记忆坚持，它迟早会退化。

VoxFlame 落地：

- 新增 `scripts/check_ai_docs.sh` 检查入口文件与核心 AI 文档是否齐全且互相引用。
- 新增 GitHub Actions 工作流，在仓库层面守住最低一致性。

## 3. VoxFlame 的 AI 编程分层

| 层级 | 载体 | 内容 | 更新频率 |
|------|------|------|---------|
| L0 | `AGENTS.md` / `CLAUDE.md` / `.github/copilot-instructions.md` | 短规则、入口地图、最低门禁 | 低 |
| L1 | `.claude-summary.md` / `.tasks/current.md` | 当前状态、任务进展、已验证结论 | 高 |
| L2 | `docs/*.md` | 稳定架构、流程、设计与约束 | 中 |
| L3 | 执行计划文档 | 单任务的目标、边界、风险、验收 | 中 |
| L4 | `scripts/` / `.github/workflows/` | 机械校验与自动化门禁 | 中 |

这套分层的目标是把“规则”和“状态”分开，把“口头约定”和“仓库事实”分开。

## 4. 什么任务必须先写计划

满足任一条件，就不应直接开改：

1. 会跨前端、后端、Agent 三层中的两层及以上。
2. 会影响主链路、会话协议、认证、记忆、TTS 打断等核心机制。
3. 需要新增外部依赖、迁移、部署步骤或数据结构。
4. 需要改动 3 个以上核心文件，或存在明确回退风险。
5. 需求本身还未收敛，需要先界定边界与验收标准。

这类任务应先根据 `docs/AI_EXECUTION_PLAN_TEMPLATE.md` 形成计划，再进入实现。

## 5. 任务执行标准

### 5.1 Research

- 先检查当前代码路径，不要拿旧结论覆盖现状。
- 外部 API、框架能力、不稳定信息优先查官方文档。
- 如果仓库已有深文档，先读对应文档，不重复造“解释版文档”。

### 5.2 Build

- 优先做最小可运行切片，不做“先大整理再开始”的空转。
- 保持接口和状态显式；不要引入 `any` 或隐式协议。
- 复杂逻辑只在必要处写短注释，避免大段低信息注释。

### 5.3 Verify

| 变更类型 | 最低验证 |
|---------|---------|
| 前端交互/UI | 目标页面 smoke test；涉及状态切换时优先 Playwright |
| 后端 API/WS | 针对受影响接口或链路的直接验证 |
| TEN Agent / 纠错链路 | 观察消息流、日志或定向脚本输出 |
| Docker / 部署 | 相关 compose/build 命令可执行 |
| 文档体系 | `bash scripts/check_ai_docs.sh` |

### 5.4 Record

任务完成后：

1. 更新 `.tasks/current.md` 中的当前状态与后续重点。
2. 更新 `.claude-summary.md` 中的项目摘要与近期里程碑。
3. 如有流程变化，更新本文件和入口文件。

## 6. 文档归属规则

不同信息必须写在正确位置：

- 入口规则：写在 `AGENTS.md` / `CLAUDE.md` / `.github/copilot-instructions.md`
- 当前状态：写在 `.claude-summary.md` / `.tasks/current.md`
- 稳定架构：写在 `docs/`
- 单次复杂任务：使用执行计划文档
- 机械检查：写进脚本或工作流

下面这些内容不应再写入入口文件：

- 某次任务的临时发现
- 某天的实现状态截图
- 旧版本路线图残留
- 只对单一功能有效的详细实现方案

## 7. 针对 VoxFlame 的特殊约束

### 7.1 产品约束

- 任何新功能都不能损害沟通成功率。
- 当准确性、时延、视觉精修冲突时，先保证可理解和可打断。
- 需要持续保留 local-first、授权边界和用户控制权。

### 7.2 工程约束

- 前端：Next.js App Router、小组件分层、状态清晰可追踪。
- 后端：Controller 只做边界处理，业务逻辑放 Service。
- Agent：要考虑会话隔离、上下文裁剪、错误恢复和广播边界。
- 数据：共享数据与用户数据边界清晰，避免把权限问题藏在实现细节里。

## 8. 反模式清单

以下做法默认视为退化：

1. 继续把 `AGENTS.md` 当成项目百科全书。
2. 依赖冗长 prompt 替代仓库内的文档、模板和脚本。
3. 没有计划就推进复杂任务。
4. 没有验证就宣布完成。
5. 把状态文档、架构文档和任务计划混写在同一个文件里。
6. 允许 `AGENTS.md`、`CLAUDE.md`、`.github/copilot-instructions.md` 长期不一致。

## 9. 维护方式

每次涉及 AI 协作机制的变更，按以下顺序更新：

1. 本文档
2. `docs/README.md`
3. `AGENTS.md`
4. `CLAUDE.md`
5. `.github/copilot-instructions.md`
6. `.claude-summary.md`
7. `.tasks/current.md`

最后运行：

```bash
bash scripts/check_ai_docs.sh
```
