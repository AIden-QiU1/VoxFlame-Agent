# VoxFlame 产品重排：从“字幕系统”回到“沟通问题”（2026-03-09）

> 这份文档用于回答一个更根本的问题：VoxFlame 接下来到底先做什么，才能真的对用户有帮助。

---

## 1. 结论先行

当前最需要调整的，不是模型栈，而是产品叙事和近期优先级。

### 1.1 应该上提为近期主线的能力

1. 帮助用户主动开口说第一句话，而不是等系统“翻译完再展示”。
2. 用场景模板、快捷短语和一键代播，让用户在陌生人、家庭、医疗场景中更快进入沟通状态。
3. 让录音 / 训练页先给用户即时反馈，再谈数据采集。
4. 把“记忆系统”先做成个体沟通档案，而不是抽象的长期存储。

### 1.2 应该降级的能力

1. 全屏字幕不应继续作为近期主叙事。
2. 它可以保留为辅助显示能力，但不应该驱动首页设计、近期路线图和产品价值表达。

### 1.3 应该单独拉出研究线的能力

1. 用户定义的硬件 / App / Web 联动。
2. 场景声音提醒与反馈给听障用户的能力，参考 Earzz。

这条线有价值，但它和“构音障碍用户先被理解”不是同一个工程切片。短期应先做架构与原型，不宜直接挤占主沟通链路的实现资源。

---

## 2. 为什么要改方向

当前仓库的真实能力已经能支撑一条更清晰的主线：

- `Frontend -> Backend -> TEN Agent` 主链路已可运行。
- ASR -> LLM 纠错 -> TTS 已接通。
- `voice_profile / memory_context` 已进入纠错链路。

但当前产品表达仍然过于像“字幕 / 翻译系统”：

- 首页直接进入聊天界面，用户看不到“产品究竟先帮我做什么”。
- 近期任务把“全屏字幕”放在过高位置。
- 训练 / 贡献页更像采数页，而不是用户能立即获得价值的训练页。

这会带来两个问题：

1. 用户无法快速理解 VoxFlame 的真正承诺。
2. 团队容易把精力继续投向展示层，而不是最小可闭环的沟通问题。

---

## 3. 外部证据与可行性判断

## 3.1 “帮助用户先开口”是科学合理的主线

ASHA 对 AAC（augmentative and alternative communication）的定义很明确：它本来就是为了补充或替代说话与写字困难人群的沟通方式，形式包括图卡、设备、App 和 speech-generating devices。

这意味着：

1. “第一句话模板”
2. “场景卡片”
3. “一键代播”
4. “短语兜底”

都不是产品发明出来的花哨交互，而是符合沟通辅助逻辑的正统方向。

对 VoxFlame 的含义：

- 不应该把自己先讲成“更聪明的字幕系统”。
- 应该把自己讲成“帮你更容易开始沟通，并在关键场景里被理解”。

## 3.2 构音障碍产品不该只盯着“识别得更准”

ASHA 关于成人 dysarthria 的临床页面也强调：管理不只是练发音本身，还包括 compensatory strategies、speech supplementation 和 AAC。

对 VoxFlame 的含义：

1. 实时理解和代播是正当主线，不是权宜之计。
2. 训练页不该只收音频数据，而应服务“补偿沟通 + 长期改善”双目标。

## 3.3 场景声音提醒是有意义的，但不应和首页主链路混在一起

Earzz 的公开产品信息说明了一件事：对听障用户而言，门铃、烟雾报警器、警笛、婴儿哭声、有人呼叫名字这类事件，本身就是高价值信息流。

这条线证明：

1. “环境声音 -> 个体提醒”是有独立价值的产品能力。
2. 用户定义硬件 / App / 可穿戴反馈，是值得做的方向。

但对 VoxFlame 当前阶段的含义是：

- 这是一个值得尽早设计架构的方向。
- 不是首页和近期 P0 的第一叙事。
- 它更适合作为“场景感知 / 硬件联动原型线”独立推进。

## 3.4 训练反馈可以做，但不能过度承诺“医学判断”

关于 speech training / biofeedback 的研究总体方向是积极的，但证据质量和泛化效果并不稳定。更稳妥的做法是：

1. 给用户可解释的即时反馈。
2. 给出趋势和可复盘信息。
3. 在没有临床验证前，不把结果包装成诊断结论。

对 VoxFlame 的含义：

- 初期训练页应该提供“目标句是什么、用户读成了什么、哪里容易混淆、近期趋势如何”。
- 不应该一开始就输出“科学诊断”或高置信医学建议。
- 更合适的表述是“练习反馈、趋势提示、后续建议”。

## 3.5 浏览器不是硬件联动的稳妥基础设施

MDN 当前对 `Web Bluetooth API`、`Web Serial API`、`WebHID API` 的说明都带有几个共同限制：

1. 依赖 secure context。
2. 兼容性有限。
3. 多数仍带有 experimental / limited availability 属性。

对 VoxFlame 的含义：

- 初期不要把硬件接入押注在 PWA 直接连设备上。
- 更稳妥的方案是：`硬件 -> App / 本地代理 -> Backend / Relay -> VoxFlame Web`。
- Web 前端更适合作为展示层和管理层，而不是唯一的设备接入层。

这是基于文档事实做出的工程推论。

---

## 4. 新的产品主张

VoxFlame 近期最应该承诺的不是“我们有 ASR + LLM + Agent + 记忆”。

而是三句话：

1. 当你不知道怎么开口时，VoxFlame 帮你先说出第一句话。
2. 当别人听不懂你时，VoxFlame 帮你更快被理解。
3. 当你想长期变好时，VoxFlame 帮你看到练习反馈和个人进展。

---

## 5. 近期功能重排

## 5.1 P0：现在就该做

### A. 首页信息架构重做

首页不该再直接把用户扔进“聊天 / 模型链路”。

应该明确 3 个入口：

1. 我现在要沟通
2. 我想练习表达
3. 我想看我的进展和记忆

### B. “第一句话 / 主动沟通”闭环

这是当前最值得优先完成的功能切片：

1. 医疗 / 家庭 / 陌生人 / 紧急场景模板
2. 快捷短语 + 用户自定义
3. 一键确认代播
4. 可打断、可回退、可重试

### C. 训练 / 录音页重做

训练页要从“采集页”改成“用户有回报的练习页”：

1. 目标句清晰可见
2. 中文普通话拼音与重点发音提示
3. 录后对照：目标句 / 识别结果 / 拼音差异 / 纠错建议
4. 单次反馈 + 趋势反馈
5. 明确告诉用户哪些数据被保存、为什么保存

这部分的实现细化见 [中文语训反馈方案](MANDARIN_PRONUNCIATION_FEEDBACK_PLAN_2026-03-09.md)。

### D. 个体沟通记忆最小模型

先别做“全量多模态长期记忆”。

先做 4 类高价值信息：

1. 用户高频表达
2. 常见混淆词 / 发音错误模式
3. 高频场景偏好
4. 训练历史与阶段性反馈

这些信息进入 agent context，才是真正有助于近期体验的记忆。

## 5.2 P0.5：尽早设计，但先不挤占主线

### E. 场景声音提醒原型

先定义：

1. 哪些声音最有价值
2. 怎么让用户自定义
3. 通过手机、手表、耳机还是独立设备反馈

首批只需要 3 到 5 个高价值事件：

- 门铃
- 烟雾报警器
- 婴儿哭声
- 呼叫姓名
- 警报 / 警笛

### F. 硬件 / App / Web 通信方案

建议近期采用三层：

1. 设备层：麦克风 / 传感器 / 边缘检测
2. App 或本地代理层：BLE / Wi-Fi / 本地事件收集
3. VoxFlame 服务层：事件统一、记忆写入、通知和展示

## 5.3 暂时降级

### G. 全屏字幕

保留，但降级为辅助能力：

1. 适合面对面展示给对方看
2. 适合特定合作方场景
3. 不再作为首页主价值和近期第一优先级

---

## 6. 对页面设计的直接含义

## 6.1 首页

首页应该先回答：

- 我今天能用它解决什么问题？
- 我应该点哪个入口？
- 它现在是不是立刻能帮我？

不应该先回答：

- 我们用了什么模型
- Agent 系统有多复杂
- 字幕展示有多炫

## 6.2 训练页

训练页的关键不是“多录”，而是“录完有没有反馈”。

如果用户每次录音后都不知道：

- 读的目标是什么
- 哪个音节总读偏
- 最近有没有进步

那么数据收集本身很难形成长期价值。

## 6.3 记忆页 / 进展页

它应该先服务三个问题：

1. 我最近哪些表达更容易被理解了？
2. 我在哪些场景最常需要帮助？
3. 系统学到了哪些真正有助于我的偏好？

---

## 7. 近期执行顺序建议

1. 先重做首页信息架构和价值表达。
2. 再完成“第一句话 / 场景沟通 / 一键代播”闭环。
3. 同时重构训练页，让录音直接产生反馈。
4. 然后把训练与沟通数据收敛进个体记忆最小模型。
5. 最后再拉出“场景声音提醒 + 硬件联动”原型线。

---

## 8. 数据与伦理边界

1. 训练反馈不等于医学诊断。
2. 趋势建议优先于结论性判断。
3. 默认最小必要存储。
4. 对每次保存、检索、删除都要有用户可理解的边界。
