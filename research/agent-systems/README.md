# 通用 Agent 系统研究

本主题研究不依赖某一种模态的 Agent 基础能力，以及这些能力如何从实验机制变成可维护、可验证、可交付的产品。它是 VoxFlame 研究体系中的“跨模态参照系”，不是新的运行时实现，也不替代 `voice-agent/` 的语音专项研究。

## 四个研究面

| 研究面 | 要回答的问题 | 对 VoxFlame 的价值 |
| --- | --- | --- |
| 通用 Agent 底层机制 | 上下文组装、状态与记忆、规划/执行、工具调用、handoff、评估与安全边界为什么有效 | 识别哪些机制是模态无关的，避免把语音问题误判成 prompt 或模型问题 |
| 工程架构 | control plane / data plane、事件与会话、可靠性、可观测性、权限、成本和部署如何组合 | 检查 `backend -> LiveKit -> livekit_agent` 是否仍是单一事实源，避免平行 runtime |
| 产品化 | 能力如何变成用户可理解、可控制、可回退、可持续使用的产品 | 把“Agent 能做什么”转成“用户在关键时刻能否完成任务” |
| 场景落地 | 在工作、医疗沟通、陌生人求助、家庭、训练和设备协同中，哪些闭环真的成立 | 用真实任务成功率、延迟、可打断性、恢复成本和信任验证抽象机制 |

## 与 Voice agent 的分工

- `agent-systems/` 研究跨模态机制、架构模式、产品闭环和场景方法；结论应能解释文本、视觉、语音等至少一种以上 Agent，或明确说明为何不能泛化。
- `voice-agent/` 研究实时语音特有的问题：ASR/TTS、端点检测、打断、音频链路、语音纠错、声学上下文和语音延迟。
- 语音 Agent 的结论必须同时经过本主题的四个问题检查：机制是否可解释，架构是否可运维，产品是否可控，场景是否改善真实沟通。
- 通用 Agent 结论进入语音产品前，必须补充语音介质的反例和门槛；文本 Agent 的成功不能直接证明语音 Agent 成功。

## 建议的对照表

每篇涉及语音的研究至少记录：

| 维度 | 通用 Agent 基线 | 语音 Agent 变化 | VoxFlame 验证信号 |
| --- | --- | --- | --- |
| 输入与上下文 | 文本/结构化事件 | 连续音频、ASR 不确定性、停顿和重叠说话 | 误识别后的修复率、上下文窗口、跨轮隔离 |
| 交互节奏 | 请求-响应 | 可打断、端点检测、半双工/全双工 | 首 token/首音频延迟、打断成功率、P95 |
| 工具与副作用 | schema tool call | 语音确认、误触发和听错风险 | 显式确认率、误执行率、审计记录 |
| 记忆 | durable / session 分层 | 语音转写噪声与隐私更敏感 | 写入精度、撤回率、跨用户泄漏为零 |
| 产品结果 | 完成一个任务 | 让陌生人真正理解用户 | 沟通成功率、补救轮次、放弃率、信任反馈 |

## 研究边界

- 不把热门 Agent 框架的功能清单当作采用依据。
- 不因为通用 benchmark 提升就直接改变语音 runtime、prompt、memory 或部署配置。
- 不建立第二套 memory、control plane 或场景执行面；应用决策仍进入 [回流登记](../APPLICATION_FEEDBACK_REGISTRY.md)。
- 涉及医疗、健康或高风险场景时，仍需专家复核、目标人群验证、隐私和合规门禁。

新增研究建议优先回答：

1. 机制在什么条件下有效，失败时如何熔断或回退？
2. 它改变的是模型能力、系统可靠性，还是用户任务结果？
3. 语音介质引入了哪些文本 Agent 没有的误差、延迟和授权风险？
4. 进入 VoxFlame 的最小切片、唯一 owner 和验证信号是什么？
